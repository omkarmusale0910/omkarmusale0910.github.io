    08:40 project 1 of 5 · Senior Data Engineer · 2026 to now

    Legal documents, LLM-ready.

    Millionsdocuments a day
    10+file formats
    60%+less data prep
    35%+less deploy overhead
    the project

    In a legal case, lawyers have to review millions of documents by hand to find the few that matter. At that scale, manual review costs weeks of effort. This platform uses AI to take the first pass: it reads every document, sorts it into legal categories, flags the important ("hot") documents and passages, and lets the team search and chat with the whole case. Lawyers review only what the AI surfaces, which cuts the manual work sharply.

    the pipeline
    1. IngestClient data lands in GCS, via Relativity or direct upload.
    2. ProcessApache Beam on Dataflow converts PDFs, Office and Google files, images, text, Markdown and legacy formats into one consistent PDF, and pulls out comments and speaker notes.
    3. CatalogDocument metadata goes to BigQuery as the working store.
    4. RAGRendered documents are ingested into a Vertex AI vector datastore for search and agentic chat.
    5. InferVertex AI batch jobs classify legal categories, rank hot documents and find hot passages, with results in BigQuery.
    6. ServeResults are mirrored to Cloud SQL (Postgres) for the app backend.
    7. OrchestrateAirflow on Cloud Composer runs every sub-pipeline, with validation checks and alerts between stages.
    my part

    I architected, built and run this pipeline end to end. I optimized the Beam pipelines on Dataflow, tuning how work is split across workers, to cut cost and raise throughput. I built the libraries that extract comments and speaker notes from Office and Google documents, which matter in legal review and feed the ML models. I wired the ML team's inference and RAG code into the pipeline, and built the validation, monitoring, alerting and CI/CD around it.

    impact

    Data prep time for the AI teams down 60%+. Deployment overhead down 35%+ through DAG automation and CI/CD. 5+ production sub-pipelines run on schedule with automatic retries and recovery.

    11:50 project 2 of 5 · Data Engineer · 2023 to 2025

    Geospatial data pipeline.

    24%lower cloud cost
    100%automated
    100 GB+TIFF imagery per run
    the project

    Insurers need to know how likely a wildfire is to reach a home or asset. This ML model predicts that risk from geospatial data: temperature, humidity, wind patterns, vegetation, urban areas, nearby water and past wildfires. All of it comes from Google Earth Engine as satellite imagery, in large TIFF files, and the model needs it fresh every week.

    the pipeline
    1. RequestAsk Earth Engine for a whole region at once, like temperature for the USA.
    2. SplitIf it fails as too big, split it into 4 chunks. A chunk that fails again is split into 4 again.
    3. MergeDownload the chunks to GCS and join them back into one TIFF.
    4. StackApache Beam stacks all the feature layers into one dataset for the ML model.
    5. AutomateIt all runs every week on its own, recovers from failures and sends an alert if something breaks.
    my part

    I owned this pipeline end to end: the architecture, the design, the split and merge algorithm, the deployment, and the full automation of the weekly export. It is scheduled with Cloud Scheduler and Pub/Sub, runs as GKE and Cloud Batch jobs, and its infrastructure is set up with Terraform.

    impact

    I optimized the pipeline by 24% with an algorithmic pre-calculation approach and by running the Kubernetes jobs on preemptible instances, which cut cloud cost. Each run processes 100 GB+ of TIFF imagery and is fully automated, with failure recovery and alerting, so nobody has to start it or watch it.
